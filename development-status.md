### Known Issues / Gotchas Discovered During Generation

- **NotebookLM cannot ingest a raw `.json` file as a source.** Adding `workflows/webhook-alert-demo.json` directly left it stuck in `"status": "preparing"` / `"type": "unknown"` forever (confirmed via `notebooklm source list --json`), which silently broke downstream generation (the `generate audio` call failed with a bare warning). **Fix**: wrapped the JSON in a fenced code block inside a `.md` file (`workflows/webhook-alert-demo-source.md`) and used that as the source instead — NotebookLM ingests it as `"type": "markdown"` and it goes `"status": "ready"` normally. If future modules need to ground on structured data files (JSON/YAML/CSV), wrap them in Markdown first.

- **The `notebooklm` CLI's "current notebook" is shared, global, per-machine state — not per-process.** Running two `generate.sh` invocations concurrently (one resumed for module 3, one already running for module 4) caused module 3's `notebooklm use <id>` call to silently redirect *all subsequent* `generate`/`download` calls from **both** processes onto module 3's notebook, since neither script calls `use` again afterward. This produced byte-identical (confirmed via `md5sum`) audio/video/slides/quiz files in `module-4-practice/content/` that were actually module 3's content. **Detected** by noticing suspiciously identical file sizes across modules, then confirming with `md5sum`, then confirming by reading quiz.md content (it was clearly about workflow nodes, not exercises). **Fixed** by deleting the 7 contaminated files (kept the legitimate pre-overlap `lesson.md`) and regenerating module 4 alone, with no other `generate.sh` process running concurrently. Re-verified via `md5sum` cross-check afterward — all clear.
  - **Lesson for next time**: `scripts/generate.sh` must be run **one module at a time, sequentially** — never in parallel — until the underlying `notebooklm` CLI supports per-invocation notebook scoping (e.g. `--notebook <id>` on every command rather than relying on `use`). This should be called out explicitly in the `lms-factory` skill's own docs; consider filing this as feedback since it's a footgun for anyone else parallelizing module generation.
